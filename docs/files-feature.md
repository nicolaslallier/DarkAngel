# File management — functional analysis

Status: draft for review · Target: `darkangel-api` + `darkangel-spa` · Date: 2026-09-20

## 1. Context and objective

DarkAngel already lets a signed-in user push files into the Infra MinIO and pull
them back. What it does not have is any *knowledge* about those files: the list
is whatever `list_objects` returns, so a file is a name, a size and a timestamp,
and nothing else. There is no way to describe a file, organise it, find it among
a hundred others, see what it looked like last week, or learn who deleted it.

The objective is to make the backend the owner of file metadata — held in the
Infra PostgreSQL — while MinIO keeps doing what it is good at: storing bytes.
The SPA grows from a single upload-and-list table into a real file manager.

The user-facing goal, in one sentence: **a user can organise, describe, search,
preview and recover their own files from the browser.**

## 2. What exists today (baseline)

Read before estimating anything — a large part of the CRUD is already written.

**Backend** — `backend/app/api/routes/files.py`

| Route | Behaviour |
|---|---|
| `GET /api/files` | Lists `<sub>/` prefixed objects; returns `{name, size, modified}` |
| `POST /api/files` | Multipart upload, unbounded size, same name overwrites |
| `GET /api/files/{name}` | Streams the object as an attachment |
| `DELETE /api/files/{name}` | Removes the object |

Isolation is by key prefix: `_prefix()` returns `f"{claims['sub']}/"`, so a user
can only ever address their own objects. `_key()` rejects a name containing `/`
or `\`, the values `""`, `.` and `..`, and anything over 255 characters — these
rules exist *only* because the display name is also the object key.

**Frontend** — `frontend/src/views/FilesView.vue`, `stores/files.ts`,
`api/files.ts`. A file input (multiple), an error line, a table of
name/size/modified, and per-row Download and Delete buttons. Download fetches a
blob and clicks a throwaway `<a>`, because the API needs a bearer token that a
plain `href` cannot carry. The store reloads the whole list after every action.

**Infra** — MinIO bucket `darkangel-files`, versioning enabled
(`scripts/provision-minio.sh:51`), reached at `minio:9000` over `infra-net`.
There is **no PostgreSQL anywhere in this repository** — no driver, no ORM, no
migrations, no service in `deploy/portainer-stack.yml`. A shared Infra Postgres
exists; DarkAngel has never connected to it.

## 3. Scope of the need

In scope, as agreed:

- **Metadata in Postgres**: tags, description, and search across them.
- **Folders**: a real tree, nested to any depth.
- **Versions and audit**: full history, restore an old version, undelete a file,
  and an append-only log of who did what.
- **Postgres as the index**: the file list is a database query, not a bucket
  listing. MinIO keys become UUIDs.
- **Limits**: a maximum file size, a per-user storage quota, and a content-type
  policy.
- **GUI**: drag & drop with upload progress; search, filter and sort; inline
  metadata editing; in-browser preview of images and PDFs.

Explicitly *not* in scope — see §14.

## 4. Target architecture and data model

### 4.1 Division of responsibility

```
Browser ──HTTPS──▶ Infra NGINX ──/api/──▶ darkangel-api ──┬──▶ PostgreSQL  (metadata, the index)
                                                          └──▶ MinIO       (bytes, versions)
```

Postgres answers *what files exist and what they are*. MinIO answers *what is
in them*. Every listing, search and sort is a SQL query; MinIO is touched only
to move bytes.

### 4.2 Object keys

The key becomes `<owner_sub>/<file_uuid>` — opaque, generated by the backend.
Consequences, all of them wanted:

- The display name is a plain column. Renaming is an `UPDATE`, not a
  copy-and-delete of the object.
- The sanitising in `_key()` stops being a correctness requirement for storage.
  Names still get validated, but as *display* data (length, control characters),
  not as path segments.
- Moving a file between folders touches no object at all. In a prefix-based
  layout, renaming a folder means copying every object beneath it; here it is
  one row update.
- Two files can share a name in different folders without colliding.

### 4.3 Schema

Database `darkangel`, owned by a scoped role `darkangel`. UUIDs are generated by
the application (`uuid.uuid4()`), not by the database: the upload path needs the
id *before* the row is written, because the id is the object key it is about to
upload to. Generating them in Python also avoids requiring the `pgcrypto`
extension, which a scoped role may not be allowed to create.

**`folders`**

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | `gen_random_uuid()` |
| `owner_sub` | `text` NOT NULL | Keycloak `sub` |
| `parent_id` | `uuid` NULL → `folders(id)` | `NULL` = root |
| `name` | `text` NOT NULL | |
| `created_at` / `updated_at` | `timestamptz` NOT NULL | |
| `deleted_at` | `timestamptz` NULL | soft delete |

Uniqueness: one name per parent per owner, among live rows. A plain
`UNIQUE (owner_sub, parent_id, name)` does **not** work, because Postgres treats
`NULL` parents as distinct and would allow two root folders called `work`. Use
`UNIQUE NULLS NOT DISTINCT` (PG 15+) in a partial index `WHERE deleted_at IS NULL`.
The Infra Postgres version has not been confirmed; on anything older than 15 the
fallback is a unique index over `COALESCE(parent_id, '00000000-…-0000'::uuid)`.

Cycles (`A` moved inside its own descendant) cannot be prevented by a `CHECK`;
a move validates with a recursive CTE walking the target's ancestors.

**`files`**

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | also the object key suffix |
| `owner_sub` | `text` NOT NULL | |
| `folder_id` | `uuid` NULL → `folders(id)` | `NULL` = root |
| `name` | `text` NOT NULL | display name, user-editable |
| `description` | `text` NULL | |
| `tags` | `text[]` NOT NULL DEFAULT `'{}'` | GIN indexed |
| `content_type` | `text` NOT NULL | as declared at upload |
| `size_bytes` | `bigint` NOT NULL | of the current version |
| `object_key` | `text` NOT NULL UNIQUE | `<owner_sub>/<id>` |
| `status` | `text` NOT NULL | `pending` \| `ready` |
| `current_version_id` | `uuid` NULL → `file_versions(id)` | |
| `created_at` / `updated_at` | `timestamptz` NOT NULL | |
| `deleted_at` | `timestamptz` NULL | soft delete = trash |

A `text[]` column with a GIN index covers tags without a join table; a
`tags`/`file_tags` pair earns its place only once tags need their own
attributes (colour, rename-everywhere), which is not asked for.

**`file_versions`**

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | |
| `file_id` | `uuid` NOT NULL → `files(id)` ON DELETE CASCADE | |
| `version_no` | `int` NOT NULL | 1, 2, 3 … unique per file |
| `s3_version_id` | `text` NOT NULL | returned by `put_object` |
| `size_bytes` | `bigint` NOT NULL | |
| `content_type` | `text` NOT NULL | |
| `created_at` | `timestamptz` NOT NULL | |
| `created_by` | `text` NOT NULL | Keycloak `sub` |

MinIO already keeps every version; this table is the readable index over them.

**`audit_log`**

| Column | Type | Notes |
|---|---|---|
| `id` | `bigserial` PK | |
| `at` | `timestamptz` NOT NULL DEFAULT `now()` | |
| `actor_sub` | `text` NOT NULL | |
| `action` | `text` NOT NULL | `upload`, `download`, `rename`, `move`, `retag`, `delete`, `undelete`, `version_restore`, `purge`, `folder_create`, `folder_rename`, `folder_move`, `folder_delete` |
| `target_type` | `text` NOT NULL | `file` \| `folder` |
| `target_id` | `uuid` NOT NULL | |
| `detail` | `jsonb` NULL | before/after values |

Append-only is enforced in the database, not by convention: the migration
grants the application role `INSERT`/`SELECT` on this table and nothing else.

### 4.4 Write consistency

MinIO and Postgres cannot share a transaction, so uploads are ordered
**row first, bytes second**:

1. `INSERT INTO files (…, status='pending')` and commit. The `id` is the key.
2. `put_object` to `<sub>/<id>`, capturing the returned version id.
3. `INSERT INTO file_versions`, `UPDATE files SET status='ready',
   current_version_id=…, size_bytes=…` in one transaction.

Every listing filters `status='ready' AND deleted_at IS NULL`, so a file is
never shown before its bytes exist. A crash between steps 1 and 3 leaves a
`pending` row and possibly an orphan object — both invisible, both cleaned by
the sweeper in §8.

The reverse order (bytes first) was rejected: it orphans objects that nothing
in the database points at, which can only be found by scanning the whole bucket.

## 5. API surface

Paths move from name-addressed to id-addressed. This is a breaking change to
the whole `/api/files` contract; the SPA is the only consumer, and the OpenAPI
snapshot regression test (`docs/testing.md` §"The OpenAPI snapshot") must be
regenerated as part of Phase 1.

**Files**

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/files` | List. Query: `folder_id`, `q`, `tag`, `sort`, `order`, `limit`, `offset`, `trashed` |
| `POST` | `/api/files` | Upload. Multipart: `file`, optional `folder_id`, `description`, `tags` |
| `GET` | `/api/files/{id}` | Metadata detail |
| `PATCH` | `/api/files/{id}` | Rename, re-describe, re-tag, move (`folder_id`) |
| `DELETE` | `/api/files/{id}` | Soft delete → trash |
| `POST` | `/api/files/{id}/undelete` | Out of trash |
| `GET` | `/api/files/{id}/content` | Stream bytes. Query: `version`, `disposition` |
| `GET` | `/api/files/{id}/versions` | Version list |
| `POST` | `/api/files/{id}/versions/{n}/restore` | Make version `n` current |
| `GET` | `/api/files/quota` | `{used_bytes, limit_bytes, file_count}` |

**Folders**

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/folders` | Whole tree for the caller |
| `POST` | `/api/folders` | `{name, parent_id?}` |
| `PATCH` | `/api/folders/{id}` | Rename / move |
| `DELETE` | `/api/folders/{id}` | Delete; `409` unless empty or `?recursive=true` |

Every route keeps taking the `Claims` dependency. Every query is filtered by
`owner_sub = claims['sub']` — the prefix isolation that MinIO gave for free
becomes a `WHERE` clause the repository layer must never omit. A missing or
foreign id returns `404`, not `403`, so the API does not confirm that another
user's file exists.

## 6. Business rules

- **BR-1 — Ownership.** A user reads and writes only rows where
  `owner_sub` equals their Keycloak `sub`. There is no sharing.
- **BR-2 — Upload of a colliding name creates a version, not a second file.**
  If a live, ready file with the same name already exists in the same folder for
  the same owner, the upload appends a new version to it. This preserves today's
  overwrite behaviour and is the natural source of version history.
- **BR-3 — Names.** 1–255 characters after trimming, no control characters, not
  `.` or `..`. Slashes are now *allowed* in a display name, because the name is
  no longer a path.
- **BR-4 — Folder names** follow BR-3 and are unique among live siblings.
- **BR-5 — No cycles.** A folder cannot be moved into itself or a descendant.
- **BR-6 — Delete is soft.** `DELETE` sets `deleted_at`; bytes stay in MinIO.
  Trashed items are excluded from normal listings and from search, and are
  visible only via `?trashed=true`.
- **BR-7 — Deleting a folder** with live children returns `409` unless
  `?recursive=true`, which soft-deletes the whole subtree in one transaction.
- **BR-8 — Restore.** Restoring version `n` server-side-copies that MinIO
  version back to the key, producing a *new* highest version. History is never
  rewritten and nothing is lost.
- **BR-9 — Quota.** An upload is refused with `413` if it would push the owner's
  total live `size_bytes` over the quota. Trashed files still count until purged,
  and so do `pending` rows: the pending insert *is* the quota reservation, which
  is why the check and the insert share one short transaction and the advisory
  lock is released before the upload to MinIO begins.
- **BR-10 — Size.** An upload over the maximum file size is refused with `413`.
- **BR-11 — Content type.** Uploads are screened against the configured policy
  and refused with `415`. Independently, only an allow-list of types may ever be
  served inline (§9).
- **BR-12 — Everything mutating is audited**, with the actor, the target and the
  before/after values. Downloads are audited too.
- **BR-13 — Search** matches case-insensitively across name, description and
  tags, scoped to the owner, excluding trash.

## 7. Use cases

**UC-1 — Upload (nominal).** The user drags three files onto the file list
while inside folder *Invoices*. For each: the SPA `POST`s multipart with
`folder_id`, showing a progress bar. The backend validates name, size, quota and
type, inserts a `pending` row, streams to MinIO, records version 1, flips to
`ready`, writes an audit entry, and returns the file. The row appears in the
table as each upload settles.

**UC-2 — Upload over an existing name (variant of UC-1).** Same folder, same
name. Per BR-2 the backend appends version 2 to the existing file instead of
creating a second one. The table shows the new size and modified date; the
detail panel now lists two versions.

**UC-3 — Organise.** The user creates *Invoices/2026*, then drags a file into
it. The SPA `PATCH`es `folder_id`. No bytes move.

**UC-4 — Describe and find.** The user opens a file's detail panel, types a
description and adds the tags `tax` and `2026`. Later they type `tax` in the
search box; the backend returns every live file of theirs whose name,
description or tags match, sorted by `updated_at DESC` by default.

**UC-5 — Preview.** The user clicks a PNG row. The SPA calls
`/content?disposition=inline`, receives the blob, and shows it in a panel via an
object URL. A `.docx` row offers download only, because it is not in the inline
allow-list.

**UC-6 — Recover an old version.** The user opens the detail panel, sees three
versions with dates and authors, and picks version 1 → *Restore*. The backend
copies that MinIO version back to the key as version 4 and audits the action.

**UC-7 — Recover a deleted file.** The user switches to *Trash*, finds the file,
and clicks *Restore*. `deleted_at` is cleared; the file reappears in its folder.
If its folder is also in the trash, the file is restored to the root and the
response says so.

**UC-8 — Quota reached.** An upload that would exceed the quota is refused with
`413` and a message naming used and available bytes. The pending row is rolled
back. The SPA shows the error next to the offending file and leaves the others
alone.

## 8. Edge cases and error handling

| Case | Handling |
|---|---|
| Upload aborted mid-stream | Client disconnect raises; the `pending` row is left and swept |
| MinIO down during upload | `502`, `pending` row swept; nothing appears in the list |
| MinIO down during list | List still works — it is a SQL query. Only content operations fail |
| Postgres down | `503` on every file route; a plain health check stays green |
| Stale `pending` rows | Swept: `DELETE FROM files WHERE status='pending' AND created_at < now() - interval '1 hour'`, and the object deleted best-effort |
| Orphan objects in MinIO | A `make reconcile` script diffs bucket against table in both directions; reported, not auto-deleted |
| Two concurrent uploads racing the quota | Both can pass a naive check. Guarded by `pg_advisory_xact_lock(hashtext(owner_sub))` around check-and-insert |
| Empty file (0 bytes) | Allowed; it is a legitimate file |
| Upload with no filename | `422` |
| Folder delete, non-empty | `409` with a count of children, unless `?recursive=true` |
| Folder move into own descendant | `409`, detected by recursive CTE |
| Restore a version whose MinIO version was lifecycle-expired | `410`; the row is marked unavailable rather than crashing |
| Same file `PATCH`ed by two tabs | Last write wins. Optimistic locking is deliberately not added (§13) |
| Very long search term / huge `limit` | `limit` capped at 200 server-side; `q` capped at 200 characters |

There is no scheduler in the stack, so the sweeper runs opportunistically at the
top of a list request rather than on a cron. It is a single indexed `DELETE`
over a tiny set of rows.

## 9. Security

- **Isolation** moves from a MinIO key prefix — which was structurally
  impossible to get wrong — to a `WHERE owner_sub = …` clause that a developer
  can forget. Mitigation: all access goes through one repository module whose
  every function takes the `sub` as its first argument, and a regression test
  asserts user B gets `404` on every one of user A's ids.
- **Inline serving is the real risk.** The SPA and the API share the origin
  `darkangel.infra.famillelallier.net`. An uploaded `.html` or `.svg` served
  inline would execute JavaScript in that origin and could read the SPA's
  tokens. Therefore: `disposition=inline` is honoured **only** for an allow-list
  (`image/png`, `image/jpeg`, `image/gif`, `image/webp`, `application/pdf`,
  `text/plain`); everything else is forced to `attachment`. SVG is deliberately
  excluded from the image allow-list. Every content response carries
  `X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox`.
- **The declared content type is untrusted.** It is stored and echoed for
  allow-listed types only; the policy check in BR-11 screens on extension and
  declared type, which stops accidents, not attackers. Byte sniffing is listed
  as an open question (§13).
- **No presigned URLs.** `minio:9000` is on `infra-net` and the Infra NGINX
  proxies only `/api/`, so a presigned link is unreachable from a browser. All
  content flows through the backend. This is a constraint, but it also means
  every byte served is authenticated and auditable.
- **Database credentials** follow the MinIO pattern: a scoped role, secret
  supplied as a Portainer stack variable, never committed.

## 10. Impacts

**Backend**

- New dependencies: `sqlalchemy>=2.0`, `alembic`, `psycopg[binary]`.
- New: `app/core/db.py` (engine, session dependency), `app/models/` (ORM),
  `app/repositories/files.py` + `folders.py`, `app/api/routes/folders.py`,
  `migrations/` (Alembic).
- Rewritten: `app/api/routes/files.py`, substantially.
- `Settings` gains `database_url`, `max_upload_bytes`, `user_quota_bytes`,
  `allowed_content_types` / `denied_extensions`, `inline_content_types`.
- Sessions stay **synchronous**, matching every existing route: plain `def`
  handlers that FastAPI runs in a threadpool, exactly as `current_claims` does
  and for the same documented reason. Async SQLAlchemy would make this the only
  async path in the codebase for no measured gain.

**Frontend**

- New: `api/folders.ts`, and components `FolderTree.vue`, `FileTable.vue`,
  `FileDetailPanel.vue`, `UploadDropzone.vue`, `FilePreview.vue`.
- Rewritten: `api/files.ts` (id-addressed, paginated), `stores/files.ts` (folder
  and query state; per-file upload state instead of one global `loading`),
  `views/FilesView.vue` (composition root).
- **`api/client.ts` needs an exception.** `fetch` cannot report upload progress.
  A single `uploadWithProgress` built on `XMLHttpRequest` must live in
  `client.ts` alongside `apiRequest`, so the "only place we call the network"
  convention holds even though it is no longer literally only `fetch`.
- The store's reload-everything-after-every-action pattern does not survive
  pagination and search; it becomes targeted updates.

**Infra**

- `scripts/provision-postgres.sh` + `make postgres`, mirroring
  `provision-minio.sh`: create database and scoped role, idempotently.
- **`scripts/provision-minio.sh` must be amended.** The policy it attaches
  (lines 53–70) grants only `s3:ListBucket`, `s3:GetObject`, `s3:PutObject`,
  `s3:DeleteObject`. Version history additionally needs
  `s3:ListBucketVersions`, `s3:GetObjectVersion` and `s3:DeleteObjectVersion`.
  Without them Phase 3 fails with `AccessDenied` against the real MinIO even
  though the versions exist. `make minio` must be re-run after the change.
- `deploy/portainer-stack.yml`: `DARKANGEL_DATABASE_URL` and a
  `POSTGRES_PASSWORD` stack variable; `.portainer.env.example` updated.
- Migrations run via `alembic upgrade head` in the API container's entrypoint.
  Safe at one replica; see §13.

**Testing and CI** — per `docs/testing.md`

- `docker-compose.test.yml` gains a `postgres` service next to `minio`.
- The `integration` job in `.github/workflows/ci.yml` gains a Postgres service
  container.
- `unit` tests cannot use SQLite: the schema relies on `uuid`, `text[]`, `jsonb`
  and partial/`NULLS NOT DISTINCT` indexes. Unit tests therefore fake the
  repository layer, and everything touching real SQL is an `integration` test.
  This shifts the unit/integration balance and puts pressure on the
  `--cov-fail-under` gate, which CI measures over the combined
  `-m "unit or regression"` run (`.github/workflows/ci.yml:41-44`) — the
  integration suite's coverage never counts toward it.
- The OpenAPI snapshot must be regenerated; a regression test per fixed
  behaviour (ownership isolation, quota, inline allow-list) as they land.

**Data migration** — one-shot, re-runnable:

1. Mirror the bucket first (`mc mirror`). This rewrites live data.
2. For each object under `<sub>/` whose suffix is not already a UUID:
   server-side copy to `<sub>/<new uuid>`, insert `files` + `file_versions`
   (version 1, `created_by` = the owner sub), delete the old key.
3. Idempotent: skip any key already present in `files.object_key`.

Accepted cost, confirmed: the copy starts a fresh version chain, so MinIO
version history predating the migration is not carried into the new keys. The
old versions remain under the old keys until step 2's delete, which is why the
mirror in step 1 is not optional.

## 11. Phasing

Each phase ships on its own and leaves the application working.

**Phase 1 — The spine.** Postgres provisioning, SQLAlchemy + Alembic wiring,
full schema created (folder columns present but unused by the UI), id-addressed
API at parity with today's behaviour, `pending`→`ready` writes, limits
(size, quota, content type), inline allow-list, audit log written, backfill
script, SPA updated to the new contract. *Visible change: almost none — and
that is the point.*

**Phase 2 — Organise and find.** Folder tree CRUD and move, rename,
description, tags, search/filter/sort with pagination. SPA gains the folder
tree, the detail panel with inline editing, and the search bar.

**Phase 3 — History and trash.** Version list, version restore, soft delete
with a Trash view and undelete, audit trail visible per file. Requires the MinIO
policy change from §10 first.

**Phase 4 — Polish.** Drag & drop with per-file progress bars, in-browser
preview for the allow-listed types, quota indicator.

## 12. Acceptance criteria

**Phase 1**

```gherkin
Given a signed-in user with no files
When they upload "report.pdf" of 2 MB
Then the response is 201 with an id, and GET /api/files lists exactly that file
And the MinIO bucket holds one object keyed "<their sub>/<that id>"
And the audit log holds one "upload" row naming them as actor

Given user A owns a file
When user B requests, patches, or deletes it by id
Then every one of those returns 404 and nothing changes

Given the maximum file size is configured
When a user uploads a file one byte over it
Then the response is 413 and no row and no object are created

Given a user whose live files already total the quota
When they upload any non-empty file
Then the response is 413 naming used and available bytes

Given MinIO is unreachable
When a user uploads a file
Then the response is 502
And GET /api/files still succeeds and does not list the failed upload

Given objects exist under the old "<sub>/<name>" keys
When the backfill script runs twice
Then each object has exactly one row, keyed by UUID, and the second run changes nothing
```

**Phase 2**

```gherkin
Given a folder "Invoices" containing a file
When the user renames the folder to "Bills"
Then the response is 200 and no MinIO object has been read or written

Given a folder tree A > B
When the user moves A into B
Then the response is 409 and the tree is unchanged

Given a root folder named "work" exists
When the user creates another root folder named "work"
Then the response is 409

Given a file tagged "tax" and another described "tax return"
When the user searches "TAX"
Then both are returned, and no other user's files are

Given a folder containing two files
When the user deletes it without ?recursive=true
Then the response is 409 naming the child count
```

**Phase 3**

```gherkin
Given a file with one version
When the user uploads a file of the same name to the same folder
Then no second file is created, and the file reports two versions

Given a file with three versions
When the user restores version 1
Then the file reports four versions, version 4 has version 1's bytes, and nothing was deleted

Given a file the user deleted
When they list files normally
Then it is absent; and when they list with ?trashed=true it is present
And when they undelete it, it returns to its folder

Given a deleted file whose folder is also deleted
When the user undeletes only the file
Then it is restored at the root and the response states that its folder is gone
```

**Phase 4**

```gherkin
Given the user drops four files onto the list
Then four progress bars advance independently
And one failing upload leaves the other three to complete

Given a PNG and a .docx
When the user opens each
Then the PNG previews inline and the .docx offers download only

Given an uploaded file whose declared type is text/html
When it is requested with disposition=inline
Then it is served as an attachment with nosniff, never inline
```

## 13. Open questions and risks

**Open questions** — none of these block starting Phase 1.

1. **Concrete limits.** What maximum file size and what per-user quota? A
   starting proposal, to confirm: 100 MB per file, 5 GB per user.
2. **Content-type policy shape.** Deny-list of dangerous extensions (simple,
   permissive) or allow-list of accepted ones (strict, higher friction)? And
   should the bytes be sniffed (`python-magic`) rather than trusting the
   declared type and the extension?
3. **Trash retention.** Do trashed files purge automatically after N days, or
   only on an explicit "empty trash"? They count against quota until purged
   either way, which users find surprising if never explained.
4. **Version retention.** Unbounded history grows MinIO forever. Cap at N
   versions per file, or an age-based lifecycle rule on the bucket?
5. **Download auditing volume.** Auditing every download makes `audit_log` the
   fastest-growing table by far. Keep it, sample it, or drop download from the
   audited actions?
6. **Duplicate names across folders** are allowed by design. Confirm that is
   wanted, since BR-2 makes a same-folder collision a new version instead.

**Risks**

- **R-1 — Ownership regression.** Isolation stops being structural. Highest
  consequence of any risk here. Mitigated by the single repository module and a
  standing cross-user regression test, but it needs review discipline forever.
- **R-2 — The backfill rewrites live data** and discards pre-migration version
  history. Mitigated by the mandatory mirror, idempotency, and a dry-run mode.
- **R-3 — Dual-write drift.** Even with `pending`→`ready`, bucket and table can
  diverge over time. Mitigated by the sweeper and `make reconcile`.
- **R-4 — Migrations on container start** race if the stack ever runs more than
  one API replica. Mitigated for now by single-replica deployment; an advisory
  lock around `upgrade head`, or a one-shot migration service, is the fix when
  that changes.
- **R-5 — Coverage gate pressure.** Moving SQL-bearing logic into the
  integration suite lowers what the gated run covers, because CI measures
  `--cov-fail-under` over `-m "unit or regression"` only. The gate may need
  rethinking rather than the tests bending to it.
- **R-6 — Scope.** Four phases is a lot. Phase 1 deliberately delivers no
  visible feature, which is the phase most likely to get squeezed — and the one
  everything else stands on.

## 14. Out of scope

- **Sharing between users**, public links, and any ACL beyond single ownership.
- Real-time collaboration, comments, or in-browser editing of file contents.
- Server-side thumbnail generation and transcoding; preview shows the original
  bytes or nothing.
- Full-text search *inside* documents. Search covers name, description and tags
  only. (A `tsvector` column is the upgrade path if the `ILIKE` + `pg_trgm`
  approach stops scaling.)
- Virus scanning of uploads.
- Resumable or chunked uploads; an interrupted upload restarts.
- Bulk operations beyond multi-file upload — no multi-select move or delete.
- Cross-device sync clients, WebDAV, or any non-browser access.
- Per-file encryption at rest beyond whatever MinIO already provides.
